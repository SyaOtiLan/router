# 个人渠道与平台渠道路由方案

## 目标

Router 给客户端保持一个 Base URL 和一枚 API Token。个人渠道由用户为自己配置，平台渠道由平台侧提供方配置；两类渠道都通过分组为用户提供模型访问服务。客户端不需要为不同渠道切换 API Key。

自动切换的现状场景、分支差异和待产品决策项见[自动切换场景矩阵](自动切换场景矩阵.md)。本方案里的自动回退章节属于目标提案，不应替代对当前行为的核对。

本方案聚焦个人渠道与平台渠道如何通过分组组成可访问服务，以及请求在组内和组间如何路由。渠道类型描述配置方、凭据归属和账单归属；分组描述用户获得什么访问服务。它们是不同层次，不能用“个人优先/平台优先”替代分组策略。

目标上，个人渠道和平台渠道尽量复用统一的逻辑渠道接口及候选处理流程，包括模型/端点能力匹配、健康判断、排序、故障分类与调用观测。两类渠道仍保留不同的所有者、凭据安全域、授权范围和费用归属；不因共用路由组件而共享用户密钥或平台账务，也不要求首期合并底层表。

当前底层模型仍不完全符合这个目标：个人连接不在 `group_channels`，平台 `Channel` 通过 `group_channels` 接入分组，公开供给报价则经 `group_supply_bindings` 单独路由。目标概念和现有对象映射的差异见[渠道规范](../模型渠道/渠道规范.md#01-目标用户概念待评审)与[分组规范](../访问控制/分组规范.md#45-目标路由层级待评审)。

## 产品对象

| 对象 | 用户看到的内容 | 运行职责 |
| --- | --- | --- |
| 个人渠道 | 用户配置的连接、协议、模型范围、凭据轮换、运行指标和验证结果 | 用户授权并配置的私有上游渠道 |
| 平台渠道 | 平台侧提供方配置并通过分组开放的服务 | 平台提供的上游渠道 |
| 分组 | 可访问模型、绑定渠道、组内路由与服务/计费边界 | 向用户和 Token 授予访问服务 |
| API Token | 可访问分组、模型范围、自动切换设置、请求限额 | 客户端调用凭证及访问范围约束 |
| 调用记录 | 实际分组、实际渠道类型与渠道、组内/组间回退、费用归属 | 可追溯性 |
| 渠道运行指标 | 1 小时、24 小时、7 天或 30 天的成功、失败、成功率、平均延迟、调用量和最近调用 | 来自真实调用日志；额度、成本或收益缺少可靠来源时明确显示不可用 |

个人渠道属于配置它的 `user_id`，不能被其他用户选择；进入某个分组候选池必须由该用户明确授权。平台渠道由平台侧配置并按分组授权给用户。公开供给服务/报价是否统一映射为平台渠道，仍须结合[开放供给方案](../开放供给/开放模型服务网关方案.md)评审，不能把现有独立报价对象直接当作已经统一。

## 当前实现基线

现有 API Token 保存 `route_policy`，字段仍以个人/社区来源表达：

- `personal_only`、`community_only` 限定当前实现的个人连接/社区候选来源。
- `personal_first`、`community_first` 表达当前个人/社区候选的优先和回退顺序。

这属于当前代码和存量配置事实，不是目标产品概念。底层 `community_*` 名称可以在兼容期保留，但用户侧新文案应统一表达为“平台渠道”，目标路由决策应按分组进行。

| 当前底层值 | 目标用户概念（待评审） | 当前运行含义 |
| --- | --- | --- |
| `personal_first` | 个人渠道优先，平台渠道回退 | 个人连接，失败后当前社区候选 |
| `personal_only` | 仅个人渠道 | 只使用个人连接 |
| `community_only` | 仅平台渠道 | 只使用当前社区候选 |
| `community_first` | 平台渠道优先，个人渠道回退 | 当前社区候选，失败后个人连接 |

当前默认值是 `personal_first`。本节保留它用于理解和迁移当前实现；目标方案不应继续把个人/平台渠道类型直接当作跨组路由策略。

## 目标路由层级（待评审）

目标路由应先处理分组，再处理分组中的渠道：

1. **确定可访问分组**：先由用户和 API Token 的授权确定请求可用的分组。未明确配置跨组策略时，只使用本次请求选定的分组。
2. **分组内选渠道**：依据该分组暴露的模型、渠道绑定、端点能力、渠道优先级/权重和健康情况选择候选。个人渠道与平台渠道若都被该分组授权，可以按组内策略参与候选；渠道类型用于呈现凭据/费用归属，不自动成为全局优先级。
3. **分组间回退**：仅在当前分组合规候选耗尽后，才考虑 Token 明确授权的备用分组及其顺序。组间回退可能改变可访问模型、倍率、额度、服务提供方或费用，必须按目标分组重新校验权限和计费，不能静默越权。

建议先评审组内策略：同模型的渠道按优先级顺序/加权选择；上游余额不足等已确认的渠道故障可尝试同组下一渠道；明确传输错误仍由独立网络重试配置控制。然后再评审是否支持 Token 配置分组回退顺序、默认是否只允许当前组，以及跨组回退的费用和权限提示。

### 分组内渠道切换：现状与期望

当前分组内候选和请求失败后的切换继续沿用现有实现。该实现存在已知问题，尤其是已绑定上游状态的请求可能不能在本次失败后转到同组其他可用渠道；当前阶段可以接受这一现状，不在本次文档中确定其修复方式。

产品期望是：同一分组仍有可处理相同模型请求的合规渠道时，某个渠道发生故障不应直接导致请求不可用，应尽可能尝试同组其他渠道。这个期望是否覆盖有状态会话，以及何种客户端请求可以安全恢复，暂不在此确定；待客户端配置和 Router 重放能力的方案明确后，再专项评审。

### 分组内故障转移（待评审）

建议为 Token 保留“上游故障时自动切换”设置，默认开启；它控制本次请求失败后是否继续尝试渠道，不定义候选归属。分组配置负责声明组内候选、排序/权重及业务倍率。候选必须属于本次已授权分组，并符合模型、端点、Token 模型范围、个人渠道所有权、用户权益、`provider_scope` 等约束。

1. 上游已明确返回额度不足、鉴权失败、模型/端点不支持、限流或服务错误时，若开启自动切换，可尝试同一分组内下一个合规渠道；这不是重复请求同一上游，不由 `RetryTimes` 决定。
2. 只有明确分类为上游传输故障时才由 `RetryTimes` 控制其他候选尝试：`do_request_failed`、`read_response_body_failed`、`upstream_transport_goaway`。客户端取消、下游写响应失败和已开始向客户端输出的响应不得重放。
3. 不因客户端错误、用户额度不足、Token 限额或客户端主动取消而切换渠道。
4. 若同一分组绑定了个人渠道和平台渠道，是否允许组内策略跨类型切换，应由分组绑定及组内候选策略明确表达。调用记录和用户展示必须说明实际渠道类型及费用归属，不能把切换描述为免费或无感。
5. 显式指定单个渠道时保持固定；除非用户另行配置并确认特定备用渠道，否则不扩大候选池。
6. 上游故障转移保持请求的模型语义不变。闭源模型切换为便宜开源模型是跨模型回退，必须由独立的逻辑模型/模型回退策略授权，并记录实际模型、原因和费用。

### 分组间回退（待评审）

分组间回退是独立于组内故障转移的第二层策略。建议默认只使用本次请求明确选定的分组；只有用户/Token 明确获准的有序备用分组才可参与回退。是否提供跨组回退、由 Token 还是分组配置备用顺序、组间模型映射与计费如何确认，尚待评审。不可因组内没有可用渠道就自动越过用户分组授权。

当前 `RetryTimes` 是二态设置：`0` 关闭，`>0` 尝试其他候选；它不是数值重试上限，也不表示重复请求同一上游。修复后它只控制明确传输错误后的候选尝试，不应作为组内 HTTP 故障转移或组间授权的总开关。管理员还可有全局关闭自动切换的运营开关，优先于 Token 设置；该开关本身不扩大可访问分组。

### Responses 会话与历史（待评审）

有状态会话如何与客户端配置、渠道绑定和 Router 重放能力配合尚未确定。本方案暂不规定上游状态标识如何处理、Router 是否保存历史或何时重放；相关方案待专项评审后补充。分组内渠道故障转移的产品期望见“分组内渠道切换：现状与期望”。

## 安全边界

1. 密钥仅在创建或轮换请求中接收，任何读取接口只返回 `credential_configured`。
2. 凭据使用 Router 已有必填 `auth.jwt_secret` 派生独立 AES-GCM 密钥加密保存；JWT 回退密钥可用于解密并完成平滑轮换。
3. 请求时才解密；日志、接口响应、错误信息都不输出 API Key。
4. 个人渠道只对所属用户的 API Token 生效，管理员的全局指定渠道语义不适用于普通用户。服务端只接受 `openai`、`anthropic`、`gemini`、`ali`、`deepseek` 五种个人文本协议，不能依赖前端下拉框阻止未知协议。
5. 连接删除后不能再被新的请求选中；已有 Responses 会话的后续调用会得到会话上游不可用，而不会切到另一账户。
6. 用户填写的 Base URL 只能是 HTTPS 公有地址，不允许用户信息、查询参数、片段、回环、内网、链路本地、CGNAT 或保留地址。实际转发使用独立 HTTP 客户端，再次解析并直连已校验的公有 IP，且不跟随重定向；它不继承 `RELAY_PROXY`，防止代理端二次解析绕过地址校验。

## 个人渠道验证和健康状态（当前实现）

当前个人渠道保存后为“未验证”。用户可主动执行“测试连接”，Router 使用与实际个人上游相同的受限 HTTP 客户端，按协议请求模型目录并验证地址可达性和 API Key 权限：

- 探测只访问模型目录，不发送推理请求，不消耗模型 Token；供应商若对其管理接口另行收费，仍以供应商规则为准。
- 连接记录保存最近一次验证时间、成功状态和经过截断的安全错误摘要；不保存或返回 API Key 明文。
- 修改协议、Base URL 或 API Key 会使旧验证结果失效；修改名称、优先级和启停状态不会。
- 验证通过说明该地址和凭据可访问模型目录，不承诺用户填写的每个模型都可用，也不替代真实调用期间的上游健康检查。
- 连接验证和模型测试不创建用户任务。管理员发起的批量模型测试会写入内部后台执行队列，以有限并发完成并逐项保存验证结果；图片、音频、视频等需要后续查询结果的用户异步业务调用继续使用独立的用户任务模型。

验证状态和运行健康必须分开展示。验证回答“配置和声明能力是否经过检查”，运行健康回答“所选时间范围内真实请求是否成功、延迟如何、是否发生熔断”。没有真实流量时不能用测试通过率冒充运行成功率。

## 端点和会话边界（当前实现）

第一批只支持文本类兼容端点：`/completions`、`/chat/completions`、`/messages`、`/responses`、`/embeddings`、`/moderations`。

当前图像、音频、实时连接、视频、文件和异步任务继续使用社区候选或固定平台渠道。原因不是协议转换困难，而是这些请求的任务资源和后续查询必须属于同一个上游账户，不能在失败时跨用户凭据转移。目标分组模型是否统一承载这些端点，仍需按任务状态和上游账户绑定关系单独评审。

Responses 的 `previous_response_id` 或工具项 ID 已绑定上游时，Router 优先保持原渠道。当前请求若仍能路由到该渠道，上游失败不会触发有状态请求的请求内重试；普通社区候选后续变为禁用或不再符合路由条件时，Router 会移除本次请求的旧状态 ID 并重新选路。个人连接和用户明确选择的社区报价不可用时仍返回 `409 Conflict`。这些处理都不会迁移原上游保存的会话内容；目标自动切换规则见 [Responses 有状态会话兼容性](Responses有状态会话兼容性.md)。

## 计费和记录（当前实现）

个人渠道不扣用户平台余额、YYC 套餐额度或 Token 金额额度；Token 的请求次数限制仍然生效。Token 金额额度在 Router 已选定平台候选后才校验，因此余额为零的 Token 仍可调用匹配的个人渠道，但不能调用平台渠道。调用记录目前仍写入兼容字段：

- `upstream_source`: `personal_provider` 或 `community_package`
- `personal_provider_id`、`personal_provider_name`
- 既有 `route_decision`、`fallback_count`、`fallback_attempts`

用户自己的调用详情展示安全路由摘要：当前策略、初始来源、实际分组、实际渠道类型和回退次数。平台渠道 ID、候选渠道、内部端点和上游原始错误属于运营拓扑，只对管理员保留。

个人渠道的成功记录应明确显示“未扣平台套餐”，其实际 API 账单由用户自己的上游供应商结算；在用户主动提供可验证账单数据前，Router 不推测或展示参考成本。平台渠道则按目标分组的服务与计费规则结算。

“我的渠道”按所选时间范围从 `event_logs` 汇总成功、失败、成功率、平均延迟、调用量、最近调用、Token 和可用额度消耗。客户端主动中止不计为上游失败，也不进入延迟与最近有效调用口径。`included_requests = 0` 且 `unlimited = true` 仍表示尚未启用个人来源套餐额度闸门；后续若启用套餐权益，应作为套餐字段加入现有 `request_quota` 权益模型，不另建用户余额，也不在个人连接中写死费用。

个人渠道参考成本和平台服务费的字段、报价和结算必须在真实收费启用时一起落库；当前不得把推测成本记为用户应付费用。

## OpenRouter 参考

OpenRouter 的 BYOK 采用加密、只写入的用户密钥，并提供用户密钥和共享容量的优先或回退选择。Router 采用相同的产品分层，但不复制其具体费率：

- OpenRouter BYOK: https://openrouter.ai/docs/guides/overview/auth/byok
- OpenRouter 上游选择: https://openrouter.ai/docs/guides/routing/provider-selection

## 公开供给边界（当前实现，目标映射待评审）

供给渠道与模型报价见 [../开放供给/开放模型服务网关方案.md](../开放供给/开放模型服务网关方案.md)。

公开供给不是个人渠道的一个开关。原连接始终是连接所有者配置的个人渠道，不会直接进入公共候选池或复用其 API Key。

用户可以从个人渠道发起“申请参与供给”，但 Router 只把名称、协议、Base URL 和模型等非敏感元数据带入一个独立的 `PublisherService` 草稿。当前它是独立运营的供给服务，使用 `publisher-service:<service-id>` 作为稳定产品身份。用户必须重新录入供给凭据，并继续完成发布者准入、连接验证、报价和运营审核。审核通过后，只有运营人员可以通过独立的 `group_supply_bindings` 把报价加入分组；报价以内部 `community-offer:<offer-id>` 句柄参与路由和结算，不会复制成 `channels` 或 `group_channels` 记录。该服务/报价未来是否统一映射成目标概念中的平台渠道，并进入统一分组候选池，需要另行评审。
