## 1. 目标

Router 为客户端提供统一的 API 入口和 Token，并在用户已获授权的服务范围内，将请求路由到可用上游。系统必须能清楚回答：

1. 用户获准使用什么服务。
2. 当前请求可以从哪些上游完成。
3. 请求失败后允许切换到哪里。
4. 实际由谁承担本次请求费用。
5. 切换之后是否仍保留请求和会话语义。

这些问题由不同对象负责，不把“分组、渠道、套餐、余额、Token 策略”合并成一个含义。

## 2. 全局心智模型

Router 的目标链路是：

```text
用户与 API Token
        |
        v
用户获得的服务权益（一个或多个服务分组）
        |
        v
本次请求的主服务分组与回退授权
        |
        v
分组共享的平台渠道 + 当前用户私有授权的个人渠道
        |
        v
按端点、模型、策略与故障状态选择上游
        |
        v
按实际服务范围和渠道来源记录费用与调用结果
```

核心原则：

1. 分组是可复用的服务定义，不是用户集合，也不是用户个人的容器。
2. 套餐或其他服务权益授予用户访问分组的权利。
3. 余额是支付能力，不单独授予模型、渠道或分组访问权。
4. 渠道提供上游能力；渠道类型说明配置责任、凭据归属和费用归属。
5. Token 可以收窄用户权限并选择路由策略，但不能扩大用户已获准的服务范围。
6. 组内换渠道、组间换服务范围、跨模型降级和有状态会话迁移是不同决策，分别授权和记录。
7. 个人渠道和平台渠道尽量共用逻辑渠道契约、候选校验、健康观测及路由处理；凭据、权限、成本和结算边界保持各自隔离。

## 3. 核心对象与责任

| 对象 | 目标职责 | 共享范围 |
| --- | --- | --- |
| 用户 | 服务权益、余额和个人资源的归属主体 | 私有身份 |
| API Token | 调用身份、可用服务范围、模型限制及路由设置 | 仅持有该 Token 的调用方 |
| 服务分组 | 模型暴露范围、共享平台渠道、组内路由和平台计费规则 | 可被多个获授权用户复用 |
| 套餐 / 服务权益 | 授予用户对一个或多个服务分组的使用权，并定义额度、次数和期限 | 按用户生效 |
| 账户余额 | 支付已获准服务请求的账户资金 | 按用户生效，不作为服务授权 |
| 平台渠道 | 平台侧配置的上游连接，可被平台授权到分组 | 按平台配置和分组授权共享 |
| 个人渠道 | 用户配置并管理的连接和凭据 | 默认由所有者自用；所有者明确加入收费分组后，可作为该分组的共享服务候选 |
| 逻辑渠道候选 | 统一表达可调用上游能力，供路由共用候选筛选和故障处理 | 平台候选按分组授权；个人候选仅在所有者授权范围内可见 |
| 个人渠道分组授权 | 允许个人渠道进入默认私有分组，或经所有者同意成为收费分组的共享候选 | 默认私有；收费组授权共享推理服务，不共享凭据 |
| 逻辑模型 | Router 对客户端暴露的稳定模型标识 | 由服务分组及 Token 范围约束 |
| 上游模型映射 | 将逻辑模型映射到具体渠道上的上游模型 | 随渠道能力和分组配置变化 |

### 3.1 分组与服务权益

分组定义技术服务范围，包括模型、端点、共享平台渠道和组内运营规则。套餐通过服务权益授予用户分组访问权；套餐是商品，分组是其对应的服务范围。

目标模型允许用户拥有多个分组权益。分组顺序与 API Token 关联，由用户为每个 Token 调整其可用分组的顺序；一次请求按该 Token 的顺序逐组寻找候选：先在当前分组内按组内策略尝试合规渠道，当前组没有可用候选或已允许的组内故障转移耗尽后，再检查顺序中的下一个已授权分组。顺序只影响该 Token 的选路，不授予新权益；Token 和模型范围仍可收窄候选，不能加入用户无权访问的分组。Token 被修改后，新请求使用新顺序，已开始的请求保持开始时读取的策略快照。

余额只有在请求已经通过服务授权后才参与支付判断。若某种充值商品同时授予特定服务范围，该授权必须由商品权益明确表达，不能从余额金额推断。

### 3.2 平台渠道与个人渠道

平台渠道由平台配置并绑定到共享分组。个人渠道始终归属配置用户。默认分组中的个人连接只供所有者使用；所有者明确加入收费分组后，该连接可为该组其他获授权用户提供服务。实现可以用独立的所有者授权/供给绑定表达，不应把个人凭据或个人连接控制权复制给消费者。

平台负责创建分组并配置分组的模型/端点范围、消费者价格、路由策略、候选审核和平台统一分成规则。普通用户不能创建或修改平台收费分组配置；个人渠道所有者只决定是否授权自己的连接加入平台开放的收费分组，并可管理该授权。用户对 Token 的分组排序属于个人路由偏好，不会改变组配置或授予组权益。

两类渠道在模型/端点能力表达、候选筛选、健康观测、故障分类和调用记录上应尽量复用同一逻辑契约与处理流程，减少重复实现和行为差异。复用的是 `ChannelCandidate` 上游调用能力与路由流程；渠道所有权、凭据隔离、可见范围、费用承担和审计归属仍需分别校验。持久化模型明确区分为 `PlatformChannel` 和 `PersonalChannel`，分别使用 `platform_channels` 与 `personal_channels`；个人渠道默认私有自用，所有者授权加入收费组后成为面向该组消费者的供给。逻辑复用不等于公开凭据或让其他用户管理该连接。

平台提供一个默认分组。用户登录后创建个人渠道时，选择该默认分组作为初始关联；默认分组提供用户自己的私有路由视图，只有该用户的 Token 能使用其个人渠道。用户之后可以明确选择将个人渠道加入平台收费分组，作为该收费分组面向其他授权用户的共享服务候选。该操作是所有者主动开放服务的授权，不公开凭据；平台组内路由按组策略在符合模型、端点和健康条件的候选中选路。

默认分组需要一种私有模型视图来暴露该用户个人连接实际支持的模型，不能把个人模型写入共享分组模型配置。关联到收费分组时，个人渠道只能承接该分组已开放、且个人连接确实支持的模型与端点。对收费分组的成功调用，按该分组规则形成服务收入；权益周期结束后确认收入分摊，并按平台统一设置且带版本的比例在平台与实际提供该个人渠道的用户之间分成。失败尝试、平台自营候选和分组中其他提供者不能错误归入该个人渠道收入。具体比例数值、净收入基数和退款/争议处理仍需在计费设计中明确。默认分组的收费方式也需明确，不能仅由分组名称推断。

所有者可以撤销个人渠道对收费分组的供给授权；撤销后新请求不得再选择该渠道，进行中的请求按明确的生效边界完成或终止。共享调用不得让消费者或平台读取个人凭据。是否要求平台审核、发布者资质、数据处理说明和服务容量承诺，以及如何处理已开始请求和历史会话，需在供给与运营细节中评审。

分组暴露的逻辑模型范围仍是边界。个人渠道只能在该范围内参与分组路由，不能借关联关系扩张分组可访问的模型或端点。用户独立使用个人渠道且不依赖平台分组的场景，继续走个人访问路径，不为每个用户创建持久化“个人分组”。

公开供给在产品概念上可归入平台提供的服务；现有发布者、报价和结算对象在生命周期统一前，应通过供给适配层参与路由，不应仅因产品改名就视为底层渠道对象已经统一。

## 4. 授权与候选资格

一个候选上游只有同时满足下列条件才可参与请求：

1. 用户和 API Token 有权访问本次请求的服务分组。
2. Token 允许本次逻辑模型和端点。
3. 分组暴露该逻辑模型，且候选渠道具有对应模型映射和端点能力。
4. 平台渠道已绑定到该分组；个人渠道要么属于当前 Token 用户并关联到其私有默认分组，要么已由渠道所有者明确授权作为该收费分组的共享候选。
5. 渠道、模型和端点满足启用状态、运营限制及安全策略。
6. Token 关联的有序分组包含该分组；组内候选遵循分组路由策略。
7. 有状态会话请求仍满足原上游绑定或经授权的历史重放条件。

分组配置、Token 策略、用户渠道授权与渠道能力只能收窄彼此的交集，任何一层都不能单方面扩大其他层授予的权限。

## 5. 请求生命周期

1. **鉴权**：识别用户与 Token，校验调用额度、模型范围和访问限制。
2. **确定服务上下文**：取得该 Token 关联的分组顺序，并与用户权益、Token 授权及模型范围取交集。该顺序只用于排序，不扩大权限。
3. **确定逻辑请求**：解析逻辑模型、端点、协议和会话状态。
4. **构造候选池**：合并当前分组的平台渠道、所有者明确授权给该收费分组的个人渠道，以及当前用户私有默认分组中的个人渠道，再应用所有授权和能力约束。
5. **组内排序与选择**：按分组优先级/权重和 Token 来源策略选择渠道。
6. **分类失败并决定下一步**：区分上游响应失败、传输错误、客户端错误、用户额度错误和会话状态错误。
7. **按序检查后续分组**：当前组没有合规可用候选，或可切换的渠道级故障导致组内候选耗尽后，按顺序检查下一个已授权分组；对目标组重新校验模型、端点、用户本地额度和计费。用户额度/权限失败、客户端错误和取消不触发跨组切换。
8. **计费与记录**：按实际成功服务分组和渠道来源结算，同时记录所有必要的尝试与故障转移轨迹。

显式指定单个渠道时默认保持固定。只有调用方明确配置备用渠道语义时，才可从固定渠道扩展候选池。

## 6. 路由与故障转移层级

| 层级 | 变化内容 | 建议默认值 | 约束 |
| --- | --- | --- | --- |
| 组内渠道切换 | 同一分组内换平台渠道或已授权的个人渠道 | Token 自动切换默认开启 | 不扩大模型、端点或服务分组范围；按实际命中渠道核算提供者分成 |
| 分组顺序选择 | 按 Token 关联的顺序查找已授权分组 | 用户可调整每个 Token 的顺序 | 顺序不授予权限；每组均重新校验权益、Token 范围和消费者计费 |
| 跨模型降级 | 切换到不同逻辑模型或质量档位 | 默认关闭 | 独立的模型回退策略，需记录实际模型和费用变化 |
| 有状态会话故障处理 | 上游绑定失效后的请求处理 | 待专项评审 | 依赖客户端配置和 Router 请求恢复方案 |

失败分类原则：

1. 上游已返回可识别的渠道级错误时，由 Token 自动切换策略决定是否尝试同组下一个合规候选；例如上游额度不足、渠道鉴权失败、渠道级限流、模型/端点不支持或上游服务错误。
2. `RetryTimes` 仅控制明确的网络传输错误后的其他候选尝试，不控制 HTTP 错误故障转移，不作为重复请求同一上游的通用次数。
3. 客户端请求错误、用户或 Token 自身额度不足、权限拒绝、客户端主动取消及已经开始输出的响应，不触发自动切换。
4. 不因一次失败就把该渠道从分组人工配置中删除或禁用；运行故障状态与运营配置分开。

Token 的“自动切换”开关控制授权候选内的故障尝试，不代表自动允许所有分组或所有模型参与。Token 关联的分组顺序决定逐组查找次序，分组内策略决定渠道候选顺序；收费组里的个人渠道只有在所有者明确授权后才具备共享候选资格。同一收费组内切换渠道不改变消费者的分组售价，但会改变实际服务提供者及平台/所有者之间的收入分配，调用和结算记录必须体现实际结果。

## 7. 计费、资产与可追溯性

| 最终使用来源 | 服务授权 | 用户侧费用归属 | Router 记录要求 |
| --- | --- | --- | --- |
| 平台渠道 | 目标分组权益 | 按目标分组套餐、额度或余额策略 | 分组、渠道、模型、计费来源、结算金额 |
| 个人渠道 | 所有者配置；收费组共享候选还需所有者发布授权及消费者分组权益 | 所有者在平台外承担模型套餐成本；收费组成功调用产生额外供给收入，由平台与渠道所有者按规则分成，用于摊薄其套餐成本 | 标明实际渠道提供者、适用分组、收入分成规则版本和费用归属 |
| 分组顺序 | 用户已授权分组的私有顺序设置 | 按最终命中分组重新计算 | 初始顺序位置、实际分组、切换原因和最终计费 |
| 失败尝试 | 候选尝试策略 | 上游失败尝试是否产生采购成本需单独定义 | 保留安全的候选尝试结果和可核算成本信息 |

平台余额或套餐额度不足属于用户侧准入/结算问题，不应通过改用另一个渠道或分组绕过限制。个人渠道默认自用，不产生平台服务收入；所有者主动加入收费分组后，该连接作为收费服务供给参与组内路由，成功调用收入按已公布的分成规则结算。所有者在平台外购买并承担模型套餐费用，分成收入是分享未用完能力带来的额外收入，用于摊薄其套餐成本，不是平台按请求报销外部账单。自用与共享供给的调用必须区分账务路径，并继续遵守 Token 调用次数、速率限制和安全策略。

调用记录至少要能回答：用户请求了哪个逻辑模型、使用哪个服务分组、实际命中哪个模型和渠道类型、发生了哪些回退、为什么切换、由谁承担费用。个人密钥、其他用户的个人渠道及不必要的内部拓扑不得暴露。

## 8. 有状态会话故障处理（待专项评审）

分组内渠道故障转移的产品期望是尽可能保持请求可用，但该期望如何覆盖有状态会话尚未确定。方案依赖客户端配置和 Router 可实现的请求恢复能力；本总体框架暂不规定客户端状态设置、会话标识处理、历史保存或重放行为，待专项方案明确后再补充。

## 9. 当前实现与目标的差距

本节用于避免把目标方案误读为当前能力：

1. 当前 `users.group` 表达单一分组；套餐订阅又按 `user_id + group_id` 运行。Token 有序分组字段和与权益的校验仍需设计。
2. 当前 `group_channels` 绑定平台渠道；个人连接仍走独立路由，没有默认组私有模型视图，也没有收费组个人渠道共享授权和分成账本。
3. 当前个人/社区来源策略仍保留 `route_policy` 兼容值；产品概念目标是个人渠道/平台渠道，不能将旧枚举直接视为目标的组间策略。
4. 公开供给报价仍通过独立的供给服务和报价绑定参与路由，尚未与普通平台渠道统一底层模型。
5. 有状态会话在渠道故障后的处理依赖客户端配置和 Router 请求恢复方案，待专项评审。

上述差距应按依赖关系逐步收敛，不通过一次重命名或一次性路由改造假定整体模型已完成。

## 10. 评审边界与后续顺序

本轮优先评审全局不变量：

1. 分组是共享服务定义，用户权益是独立的用户级授权。
2. 余额是支付来源，不自动授予新的服务范围。
3. 个人渠道所有权和凭据保持私有；创建时选择平台默认分组供本人使用，也可由所有者明确授权加入收费组，为该组其他消费者提供服务。
4. 组内切换、组间回退、跨模型降级和有状态迁移是不同层级。
5. 每次实际路由和计费都可解释、可追溯，切换不绕过授权。

框架通过后，后续按以下顺序细化：
