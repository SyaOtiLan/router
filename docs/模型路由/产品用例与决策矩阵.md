# 产品用例与决策矩阵（待评审）

## 文档状态

- 状态：产品用例评审稿
- 用例描述目标行为，不代表当前实现
- 用例用于验证[服务授权与渠道路由总体方案](./服务授权与渠道路由总体方案.md)，并决定功能取舍
- 本文通过评审前不据此修改代码；具体字段、接口、页面与迁移另行设计和评审

用例优先级含义：`P0` 表示必须进入本轮产品框架评审、影响核心承诺；不代表该用例中的所有高级能力都必须首期交付。`P1` 表示可在核心服务闭环之后评审或推进。

## 1. 目的与评审方式

先从用户要完成的事推导产品能力，再决定对象和实现细节。本文刻意不以“支持某个字段/开关”作为用例，而是描述用户目标、成功结果、失败时的预期和需要作出的产品决定。

评审每个用例时，重点确认：

1. 这是目标用户的真实核心目标，还是少数边缘能力？
2. 成功时用户得到什么可观察结果？
3. 失败时应该继续、切换、等待配置，还是明确拒绝？
4. 是否改变可访问的服务、模型、数据去向或费用承担方？
5. 用户是否能事先理解并控制这种变化？
6. 哪些能力是首期必要，哪些可以后置？

## 2. 参与者

| 参与者 | 目标 |
| --- | --- |
| 应用开发者 / API 使用者 | 用一个稳定入口和 Token 调用获准的模型服务，获得可预测的错误与费用结果 |
| 个人渠道所有者 | 配置自己的凭据和连接，并确定个人资源何时参与调用 |
| 平台运营人员 | 配置平台服务范围、渠道、分组、套餐权益和故障治理 |
| 独立服务提供者 | 发布经过准入、验证和审核的独立模型服务并查看调用和结算 |
| 支持 / 财务人员 | 根据调用记录解释请求实际使用的服务、故障转移和费用归属 |

## 3. 目标用例

### UC-01：用户首次通过平台服务完成 API 调用（P0）

**场景**：用户获得一个平台套餐或服务权益，创建 Token，并用兼容客户端请求授权范围内的逻辑模型。

**成功结果**：请求只进入用户有权使用的服务范围；返回模型响应；用户能查到实际模型、服务来源、扣费来源和用量。

**异常结果**：Token 无权访问模型、套餐/额度不满足、没有可用渠道时，返回可区分且可行动的错误，不用其他未授权模型或分组兜底。

**验证的问题**：用户购买的是套餐权益、某分组的访问权，还是预付余额？用户是否需要直接认识“分组”这一后台概念？

### UC-02：用户只用自己的个人渠道（P0）

**场景**：用户录入自己的上游凭据，使用 Router Token 调用个人渠道支持的模型；用户没有平台套餐，或明确选择不使用平台服务。

**成功结果**：只有渠道所有者自己的 Token 可调用该连接；Router 不把个人凭据用于其他用户或公共供给；调用仍受 Token 调用次数、速率、安全策略约束；记录说明未扣平台推理费用。

**异常结果**：个人渠道配置失效或不可用时，不自动借用平台额度或其他用户的个人渠道。

**验证的问题**：个人服务是否是与平台分组并列的访问路径，还是个人渠道也必须绑定到一个服务分组？目标模型建议不为每个用户创建实体“个人分组”。

### UC-03：用户同时拥有个人渠道与平台服务，并选择来源策略（P0）

**场景**：用户既有平台服务权益，也配置了个人渠道。用户为 Token 选择仅个人、仅平台，或在允许的来源之间指定优先顺序。

**成功结果**：请求按预先配置的来源范围和顺序路由；个人渠道仅对该用户生效；若一次请求切换了费用承担方，调用记录能明确显示实际来源和费用归属。

**失败结果**：未授权或未配置的来源不因自动切换开关开启而加入候选池。

**验证的问题**：默认来源策略是什么？Token 级设置是否足够，用户是否还需要按模型或分组设不同策略？跨个人/平台来源切换是否必须单独显式开启？

### UC-04：某个上游渠道故障，系统在同一服务范围内继续完成请求（P0）

**场景**：同一逻辑模型、同一端点在当前授权分组内有多个合规渠道；初选渠道余额耗尽、渠道鉴权失效、渠道限流、模型/端点不支持或上游服务异常。

**成功结果**：若 Token 自动切换开启，Router 按分组候选顺序尝试下一个合规渠道；请求的逻辑模型和服务授权范围保持不变；记录初选和最终命中的渠道及原因。

**禁止行为**：不把渠道临时故障自动写回人工分组配置；不因用户侧额度或权限不足而切换上游绕过准入；不静默切换到另一逻辑模型。

**验证的问题**：哪些上游错误可触发候选切换？Token 自动切换默认开启是否仍是合适默认值？明确网络错误和已收到 HTTP 错误如何分别处理？

### UC-05：平台上游额度与用户自己的额度分别耗尽（P0）

**场景 A：平台渠道的上游余额不足。**这是平台供给侧渠道故障。若同组仍有合规候选，可按 UC-04 和 Token 策略切换。

**场景 B：用户的平台套餐额度、次数或余额不足。**这是用户侧准入或结算条件，不等于上游渠道故障。

**目标结果**：场景 B 默认不能靠换另一个平台渠道绕过用户侧限制。若用户事先为 Token 明确配置了个人渠道备用来源，是否允许在平台额度耗尽时转到个人渠道，必须由独立、可理解的来源策略决定；不得由系统隐式假设用户愿意承担自己的上游账单。

**验证的问题**：平台余额/套餐耗尽时，产品是否允许预先授权的个人渠道继续服务？若允许，用户如何识别这次请求将改由个人上游结算？

### UC-06：同一用户拥有多个服务分组或权益（P0）

**场景**：用户同时有多个套餐/服务权益，同一个逻辑模型可能出现在多个分组中，但分组的价格、渠道、数据规则或服务质量不同。

**成功结果**：请求有确定的主分组；用户或管理员可解释为什么该请求使用此分组及其计费规则。若启用备用分组，只有明确授权的有序分组可被尝试，并对目标组重新校验模型、端点、权益与计费。

**默认建议**：不因某分组耗尽或不可用而自动进入另一个分组；组间回退默认关闭。

**验证的问题**：分组由 Token 绑定、请求参数选择，还是用户账户默认值决定？同模型多分组的优先级由谁配置？套餐是否允许一个商品授予多个分组？

### UC-07：有状态会话遇到上游故障（处理方式待专项评审）

**场景**：用户在持续使用的会话中遇到原上游不可用，希望继续完成当前任务。

**产品期望**：尽可能减少会话中断，同时保留用户请求的上下文和工具行为语义。

**待确定**：具体处理依赖客户端会话配置和 Router 请求恢复能力。本用例不预设客户端状态设置、Router 历史保存、会话标识处理或请求重放方案；相关决策待专项评审后补充。

### UC-08：调用方显式指定渠道（P0）

**场景**：应用请求中指定了某个渠道或显式报价，通常是为了数据区域、测试、供应商能力或合同要求。

**成功结果**：默认固定使用调用方指定的对象；失效时明确失败。只有调用方显式配置备用集合及其含义，才可继续选择其他对象。

**验证的问题**：现有“显式选择报价”和“管理员固定渠道”是否需要统一为同一种固定路由语义？哪些参数属于用户可见的稳定 API？

### UC-09：平台运营人员建立并维护可售服务（P0）

**场景**：运营人员配置平台渠道、模型映射、服务分组、分组渠道优先级/倍率，并向用户提供套餐或服务权益。

**成功结果**：运营人员能分别管理人工配置与运行健康；临时故障可告警、降权或人工处置，但不会静默改变用户可见的服务范围和商业规则；新用户获得的默认权限是最小且明确的。

**验证的问题**：谁拥有分组模型范围、谁可将渠道加入分组、谁能授予用户分组权益？哪些故障动作可自动化，哪些必须运营确认？

### UC-10：独立服务提供者发布模型服务供消费者使用（P1，现有独立供给流程）

**场景**：提供者完成准入，使用独立凭据配置服务，通过验证、报价和审核后向消费者开放；运营可将公开报价加入受控分组候选。

**成功结果**：个人自用凭据不被复用或公开；消费者可理解服务提供者、价格和数据规则；调用费、平台服务费和提供者应收可审计。

**验证的问题**：用户侧是否统一称为“平台渠道/平台服务”，而后台仍保留“平台自营”和“独立运营供给”的结算差异？报价是否继续作为路由适配对象，而非强行合并为普通 `Channel`？

### UC-11：用户或支持人员解释一次失败、切换与账单（P0）

**场景**：用户发现请求失败、模型响应变慢、额度变化或实际来源与预期不同，需要理解发生了什么。

**成功结果**：用户能看到请求模型、服务范围、实际来源类型、是否发生切换、失败的用户可理解原因及扣费结果。支持/财务角色在授权范围内可查看内部渠道、尝试轨迹和采购/结算归因。

**隐私边界**：不展示 API Key、其他用户的个人渠道或不必要的上游内部拓扑；外部个人上游账单没有可靠数据时不推测成本。

**验证的问题**：哪些信息是用户的自助排查必需，哪些仅管理员可见？失败的上游尝试是否可能产生采购成本，需如何记账？

## 4. 关键失败场景矩阵

| 失败场景 | 问题归属 | 目标处理方向 | 是否能自动换渠道 |
| --- | --- | --- | --- |
| 平台渠道上游余额耗尽 | 供给侧渠道故障 | 当前组下一个合规候选 | 可，受 Token 自动切换设置控制 |
| 平台渠道凭据被上游拒绝 | 供给侧渠道故障 | 当前组下一个合规候选；记录错误并告警 | 可，受策略控制 |
| 明确网络传输错误 | 请求传输故障 | 按独立传输尝试规则处理；保护已输出响应和客户端取消 | 可尝试其他候选；由 `RetryTimes` 对应规则控制 |
| 用户套餐/请求次数/余额不足 | 用户准入或支付 | 按套餐与余额策略拒绝或既定余额兜底 | 不应通过另一个平台渠道绕过；预先配置的个人来源回退待决策 |
| Token 无权访问分组或模型 | 授权失败 | 拒绝请求 | 否 |
| 当前分组不暴露该逻辑模型 | 服务范围不匹配 | 拒绝或提示使用获准模型 | 不自动跨模型；不自动换组 |
| 渠道不支持请求端点 | 候选能力不匹配 | 从候选池预先排除；无候选则给出能力错误 | 可选其他满足端点条件的同组渠道 |
| 客户端主动取消 | 调用方取消 | 停止上游处理并释放预占 | 否 |
| 已开始向客户端流式输出后上游中断 | 响应已部分交付 | 结束流并记录部分失败，避免重放产生重复输出/副作用 | 否 |
| 有状态会话遇到上游故障 | 会话持续使用受影响 | 处理方式待客户端配置与 Router 请求恢复方案明确后专项评审 | 暂不规定 |
| 显式渠道/报价失效 | 固定路由约束 | 明确失败 | 默认否；仅使用显式配置的备用集合 |

## 5. 需要评审的产品决策

| 决策 | 用例依据 | 建议方向 | 若选择相反方向的主要代价 |
| --- | --- | --- | --- |
| D1. 分组是什么 | UC-01、02、06、09 | 可复用的服务定义；不代表用户集合 | 若作为用户分区，多权益、共享商品和跨组服务会混在一起 |
| D2. 用户如何获得分组访问权 | UC-01、06 | 套餐/明确服务权益授予一个或多个分组；Token 只能收窄 | 若用余额隐式授权，无法清楚说明用户买到了什么服务 |
| D3. 用户能否拥有多个分组 | UC-06 | 目标上支持；需明确主组选择与每组权益 | 若维持单组，套餐、Token 与用户组字段语义难以统一 |
| D4. 请求主分组如何确定 | UC-01、06、08 | Token 显式绑定/默认主组；存在歧义时不静默猜测 | 自动选择可能造成不同价格、数据区域或服务质量下的意外路由 |
| D5. 个人渠道如何进入候选池 | UC-02、03 | 用户私有授权关联到服务上下文；不写入共享 `group_channels`；个人独立路径保留 | 创建个人分组增加管理和权限对象；共享绑定会造成跨用户泄露风险 |
| D6. 默认是否允许平台/个人来源混合 | UC-03、05 | 由 Token 明确限定来源和顺序；先评审默认值，不因总开关自动扩大来源 | 自动混合会让费用承担方在请求中变化；完全禁止则减少故障恢复弹性 |
| D7. 哪种额度不足可触发来源回退 | UC-04、05 | 上游渠道额度不足作为渠道故障；用户额度不足不自动绕过。个人备用是否允许须显式预授权 | 不区分两种额度会把平台经营故障和用户欠费/权益耗尽混为一谈 |
| D8. 组内故障转移默认值 | UC-04 | 延续 Token 级自动切换默认开启的提案，但只在已授权、同组、同模型的候选内 | 默认关闭降低可用性；无范围限制的默认开启会扩大授权或费用风险 |
| D9. 组间回退默认值 | UC-06 | 默认关闭，明确配置有序备用组后才允许 | 自动跨组可能改变价格、模型范围、数据规则和套餐扣减对象 |
| D10. 跨模型降级是否自动 | UC-04、06 | 首期默认关闭，独立映射和授权 | 低成本模型可能不满足任务质量、工具调用或上下文要求 |
| D11. 有状态会话如何应对上游故障 | UC-07 | 期望尽可能保持会话可用；具体方案待客户端配置和 Router 请求恢复设计明确后专项评审 | 未确认请求是否可恢复前，过早决定行为可能造成上下文或工具语义问题 |
| D12. 公开供给是否统一为平台服务概念 | UC-10 | 用户侧产品概念可归为平台提供的服务；运营、结算和底层适配暂保留差异 | 立即统一底层对象会抹平发布者应收、审核与平台采购成本差异 |
| D13. 调用记录展示范围 | UC-03、08、11 | 用户看得到自身路由结果和费用归属；内部拓扑按角色授权 | 信息过少难排障，信息过多暴露上游和其他用户资源 |

## 6. 能力优先级建议

这是评审建议，不是已经批准的迭代承诺。

### 首期核心闭环

1. 用户/Token 对服务范围的明确授权和主分组确定。
2. 平台渠道与用户个人渠道的隔离及候选资格规则。
3. Token 可理解地配置来源范围与同组自动切换。
4. 用户额度失败与上游渠道失败的处理区分。
5. 实际服务、来源和费用归属可查。
6. 有状态会话故障后的恢复方式待专项评审；当前先不固化策略。
7. 平台运营可以配置、检查和解释分组服务。

### 后续能力

1. 有序组间回退；多分组下的主服务选择仍需在首期授权模型中明确，不能因此静默跨组。
2. 根据专项评审结果决定是否支持有状态会话故障恢复及其实现方式。
3. 自动跨逻辑模型降级与高低档模型组合。
4. 更细的按模型、端点、时间和预算维度来源策略。
5. 公开供给和平台自营服务的统一底层路由对象。

若评审确认多分组授权和确定性选组是首期不可缺少的产品能力，则“多分组主选”应从后续项提升为首期核心；这取决于实际套餐销售与用户持有多个权益的场景，而不是实现便利性。

## 7. 从用例到设计的依赖顺序

1. 先确认 UC-01 至 UC-11 的用户目标、优先级和边界。
2. 依据 D1-D5 确定服务授权、权益、Token 主组与个人渠道私有关系。
3. 依据 D6-D10 确定来源策略、失败分类、组内/组间/跨模型边界。
4. 依据 D11 评估有状态会话故障恢复的目标、客户端前提与 Router 能力。
5. 依据 D12-D13 确定开放供给的产品概念、调用详情与运营可见性。
6. 以上评审通过后，再形成数据模型/API/UI/迁移设计；设计评审通过后才改代码。
