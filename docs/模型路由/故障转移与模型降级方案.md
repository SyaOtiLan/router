# 故障转移与模型降级方案

## 文档状态

- 状态：评审稿（2026-11-03）
- 目的：给出一套可以直接落地的渠道故障转移与模型降级方案，取代此前“先重构分组/权益/个人渠道对象模型，再做故障转移”的路线
- 立场：先明确渠道故障转移和模型降级的产品边界，再按层评审是否实现；有状态会话的故障处理暂不纳入本方案，待专项评审

## 1. 先回答最初的问题

最初的问题是：多个上游渠道余额不同，余额少的用完后，持续会话遇到 `409 已绑定的 Responses 会话上游不可用`，不能自动切到仍可用的渠道。

当前可确认的是，Responses 状态识别、渠道绑定和请求内故障转移之间存在耦合：

| 事实 | 位置 |
| --- | --- |
| 当前代码存在 Responses 状态识别、渠道绑定和请求内故障转移之间的耦合 | `internal/relay/responsestate/state.go`、`internal/admin/controller/relay.go` 及相关转发逻辑 |

当前证据尚不足以确认客户端请求能否完整恢复，也不足以确定客户端配置与 Router 请求重放的职责边界。因此本方案不判断具体会话状态原因，也不规定相应修复方式；该问题待专项方案明确后处理。

## 2. 总原则

一句话：**故障转移是在已授权候选池内尝试其他上游；渠道故障转移与模型降级是独立策略；有状态会话遇到故障后的处理暂缓，待客户端配置和 Router 请求恢复方案明确后专项评审。**

当前纳入讨论的路由层级：

| 层 | 决策 | 默认 | 候选边界 |
| --- | --- | --- | --- |
| L1 | 同一分组内换渠道 | Token `auto_failover` 开（提案） | 当前分组 × 同模型 × 同端点 × `provider_scope` |
| L2 | 换到下一个分组 | 按 Token 关联的分组顺序（提案） | 仅限用户和 Token 已授权的分组；每组先耗尽组内合规候选 |
| L3 | 换到另一个模型 | 关；只在请求逻辑模型别名时生效（提案） | 别名定义的有序模型列表 |

不做的事：

1. 平台提供一个默认分组，用户添加个人渠道时选择该组；所有者也可明确授权将个人渠道加入收费分组，供该组其他消费者调用。共享推理服务能力，不共享凭据；成功调用收入由平台与实际渠道所有者按规则分成。
2. 暂不决定有状态会话故障处理、客户端配置或 Router 请求重放方式；该问题单独评审。
3. 分组顺序关联到 Token，用户可为每个 Token 调整其已授权分组的顺序；权益来源的系统优先级不再代替 Token 顺序。
4. 不改 `RetryTimes` 语义，它继续只管三类明确传输错误。

## 3. 有状态会话问题（暂缓）

渠道切换的产品期望是：当前分组仍有合规可用渠道时，尽量继续完成请求。该期望如何覆盖持续会话，取决于客户端是否关闭相关状态行为以及 Router 能否安全恢复请求；目前两者的配置和方案尚未确定。本节不提出状态判定、标识改写、历史存储、重放或错误码设计。上述前提明确后，再单独形成方案评审。

## 4. L1：组内故障转移

现有能力已经覆盖大部分，需要补齐五件事：

1. **Token 级 `auto_failover` 布尔字段**，默认开；管理端增加全局开关，关闭时优先。关闭的含义：上游 HTTP 错误（额度、鉴权、限流、5xx、能力错误）不换渠道；`RetryTimes` 管的传输错误不受此开关影响。
2. **个人连接之间可转移**。当前 `community_first` 回退个人时只试 `personalChannels[0]`，`personal_first` 下个人连接失败直接转平台，不试第二条个人连接。改为同一来源内先耗尽再跨来源。
3. **分组绑定的报价参与转移**。当前只要首选渠道是 `offer:` 就关闭全部重试，把“分组通过 `group_supply_bindings` 绑定的报价”和“用户显式选的报价”混为一谈。前者是普通候选，应可转移；后者保持固定。另外 `offer:` 渠道的 provider 固定为 `community_offer`，在默认 `retry_scope=same_provider` 下与托管渠道互不可达，需要让报价继承其真实 provider。
4. **重试阶段重新套 `provider_scope`**。当前重试只检查 `retry_scope`，没有应用白名单/黑名单；首次选路是均匀随机，重试是加权，两者要统一。
5. **加上限**。当前 HTTP 错误的转移没有次数上限，会一直试到候选耗尽。建议：单请求总尝试次数上限（含首次）默认 4，总耗时预算默认 60 秒，均为系统设置。

个人渠道与平台渠道作为同一分组中的候选时，按该组策略和候选顺序处理，不再由 `route_policy` 表达跨组顺序。存量 `route_policy` 的兼容和迁移另行设计：

| `route_policy` | 允许的跨来源方向 |
| --- | --- |
| `personal_first` | 个人耗尽后 → 平台 |
| `community_first` | 平台耗尽后 → 个人 |
| `personal_only` / `community_only` | 不跨 |

用户侧文案把“社区”改为“平台渠道”，字段值兼容期不改。调用记录已有 `UpstreamSource`，切换后要更新为最终来源，并在用户用量页标明“本次由个人渠道承担”。

## 5. L2：按用户顺序切换分组

现状：首次选路时 `SelectEntitlementChannelForRequest` 按系统权益来源顺序逐组找候选，某组没有候选就看下一组；但请求失败后的重试循环把分组固定，候选耗尽即结束。目标行为改为用户可调整已授权分组的顺序，并按该顺序逐组处理。

方案：把初次选择和故障后切换统一成“Token 有序分组列表 × 组内候选”。每个分组内先按其路由策略耗尽合规渠道；当前组没有候选或由可切换的渠道级故障导致候选耗尽后，再进入下一已授权组。进入下一组时重新校验用户/Token 权益、模型、端点、本地额度，重新计算模型映射、倍率和计费来源，并把 `RouteDecision.group_id` 更新为实际使用的分组。

按 Token 设置的分组顺序查找；自动切换关闭时不得因上游故障继续进入后续组。组间切换会改变本次适用的套餐/分组计费规则，因此调用记录和用户账单必须显示实际命中的组及扣费来源。用户本地额度、次数或授权不足应终止请求，不得通过后续组绕过限制。

待详细设计：Token 顺序如何随授权变化而更新；用户调整顺序后在途请求是否保持旧顺序；用户持有同模型但价格或服务规则不同的多个组时，如何在用量页呈现组间切换和最终扣费。

## 6. L3：模型降级（高低搭配）

渠道转移全程不改模型。换模型用一个独立对象表达授权：**分组级逻辑模型别名**。

- 管理员在分组内定义别名，例如 `coding-auto` → `[gpt-5.6-sol, deepseek-v4]`，有序。
- 别名出现在分组模型列表里，Token 的模型范围按别名授权。
- 请求别名即表示授权降级；请求具体模型永不降级。这样授权语义由模型名自解释，不需要 Token 再加开关。
- 触发顺序：先对列表第一个模型做完 L1、L2；全部耗尽后才换第二个模型，再做 L1、L2。
- 有状态会话的模型降级行为暂不定义，待专项评审。
- 可追溯：`RequestModelName` 记录别名，`ActualModelName` 记录实际模型，新增响应头 `X-Router-Actual-Model`；计费按实际模型。
- Codex 使用方式：`config.toml` 的 `model` 填别名。

不选“Token 级 model_fallback 开关 + 分组降级链”的原因：用户请求了明确模型名，却可能拿到另一个模型的回答，这种意外只能靠文案解释；别名方式让每个请求的模型语义在请求体里就是明确的。

## 7. 错误分类总表

| 失败 | 归属 | L1 组内 | L2 跨组 | L3 换模型 |
| --- | --- | --- | --- | --- |
| 上游额度不足、渠道鉴权失败、429、5xx | 渠道故障 | 是（提案） | 是（提案） | 是（仅别名） |
| 模型/端点不支持 | 能力不匹配 | 是（提案） | 是（提案） | 是（仅别名） |
| `do_request_failed` 等三类传输错误 | 传输 | `RetryTimes>0` 时 | 同左 | 同左 |
| 用户套餐/余额/Token 限额不足 | 用户准入 | 否 | 否 | 否 |
| 普通 400/422、内容安全拒绝 | 客户端 | 否 | 否 | 否 |
| 客户端取消、已开始输出 | 不可重放 | 否 | 否 | 否 |
| 指定渠道、用户显式报价 | 固定路由 | 否 | 否 | 否 |
| 有状态会话原上游不可用 | 会话故障 | 待专项评审 | 待专项评审 | 待专项评审 |

## 8. 可追溯性

`FallbackAttempt` 增加 `group_id`、`source`（platform/personal/offer）、`model`、`skip_reason` 和 `final_group_id`。用户用量页展示：请求模型、实际模型、实际来源、是否发生切换、费用归属。管理端按角色展示完整尝试链。有状态会话相关的观测字段待专项方案确定后再评审。

## 9. 实施顺序

每步一个 PR，可独立发布，前一步不依赖后一步：

| 步 | 内容 | 涉及文件 | 规模 |
| --- | --- | --- | --- |
| 1 | L1 的五项补齐，含 Token `auto_failover` 字段迁移与前端表单 | `model/token.go`、`relay.go`、`routing/policy.go`、web Token 页 | 中 |
| 2 | L2 重试循环跨权益分组，日志更新最终分组 | `relay.go`、`routeobs` | 小 |
| 3 | L3 分组模型别名表、分发与重试接入、管理端配置、响应头 | 新表与 migration、`distributor.go`、`relay.go`、管理端 | 中 |

以上是故障转移和模型降级的候选实现步骤，均需按产品决策评审后推进。有状态会话相关问题不包含在这些步骤中。
