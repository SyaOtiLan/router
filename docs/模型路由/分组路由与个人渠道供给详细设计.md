# 分组路由与个人渠道供给详细设计（评审稿）

## 1. 文档状态与范围

- 状态：产品与数据设计基线；阶段一 Token 分组顺序持久化已实现并已完成生产升级，但尚未接入真实选路。原阶段二影子路由已决定取消，本次清理其 Router 实现；后续改由 Tester 隔离环境 E2E 验证，Tester 用例仍待评审后实施。
- 承接[服务授权与渠道路由总体方案](服务授权与渠道路由总体方案.md)已确认的方向：Token 关联有序分组；每组先路由组内候选；个人渠道默认关联平台默认分组供所有者自用；所有者可主动加入收费分组；收费成功收入在平台与实际渠道所有者之间分成。
- 本文细化候选对象、请求流程、费用分配、授权撤销和迁移边界。已确认周期结束后再确认该周期供给分成，分成比例由平台统一设置；首期结算币种建议为 CNY。具体比例数值、净收入基数和结算风控细节仍需评审。
- 当前代码与本文目标存在差距；本文评审通过前不据此修改代码。

## 2. 产品不变量

1. **Token 的分组列表只表达顺序。**用户是否有权使用某组仍由有效权益决定；Token 的模型限制、状态、额度和其他安全规则继续生效。组顺序不能获得新权限。
2. **先组内、后组间。**按 Token 中的顺序逐组检查。初次选路时若某组没有匹配候选，继续检查下一组；候选已经被调用后，只有允许的渠道故障转移耗尽本组候选，才因上游错误继续到下一组。
3. **不同错误采用不同边界。**上游渠道级错误可按自动切换设置尝试下一个候选。只有明确的上游传输错误受 `RetryTimes` 控制。用户额度/次数不足、权限错误、Token 错误、客户端错误和客户端取消不触发下一组。
4. **分组决定消费者服务价。**同一收费分组中，平台渠道或个人渠道成功提供相同逻辑模型服务时，消费者适用同一分组/模型价格，不按渠道偷偷改价。组内候选渠道不得再配置消费者售价倍率。
5. **所有者授权的是服务能力。**默认组里的个人连接仅供所有者本人调用。所有者把连接加入收费分组后，该连接才成为该组面向其他消费者的候选；消费者不能读取凭据或管理连接。
6. **个人渠道分成是供给收入，不是上游费用报销。**渠道所有者在平台外购买并承担模型套餐费用；将未用完的额度/能力授权给收费分组后，其他用户的成功调用为所有者带来额外收入，用于摊薄套餐成本。平台不承担或逐请求报销所有者的上游套餐费用，也不把固定套餐成本伪装成单次采购成本。分成归属到本次成功请求实际命中的个人渠道所有者；未命中的候选不获得该次成功服务收入。
7. **当前只规划无状态请求。**Responses 等有状态会话如何跨上游恢复仍按专项方案处理；本设计不定义会话内容存储或重放。
8. **分组由平台治理。**收费分组由平台创建和维护；分组开放模型/端点、消费者价格、路由策略、可接入渠道、平台分成比例及供给治理规则均由平台管理员配置。普通用户可选择是否购买/使用自己有权益的分组，可为 Token 调整已授权分组顺序，并决定是否授权自己的个人渠道加入平台开放的收费分组；这些用户操作不修改分组配置或新增访问权。

## 3. 概念关系

### 3.1 持久化模型与路由候选命名

为避免个人供给接入和分组候选统一时扩大改名成本，代码从本阶段起采用以下边界：

- `PlatformChannel` 持久化平台配置的上游渠道，表名为 `platform_channels`。
- `PersonalChannel` 持久化用户拥有的个人渠道，表名为 `personal_channels`；凭据仍只在该模型内加密保存。
- `ChannelCandidate` 是路由运行时契约。平台渠道、个人渠道及公开供给适配器分别生成候选；候选携带来源类型和所有者范围，但不会把凭据序列化到客户端响应或日志。
- 平台和个人渠道保持独立的所有权、权限、账务和生命周期；共用候选行为不合并持久化表。
- 现有 `channels`、`personal_provider_connections`、`personal_model_routes` 通过版本化数据库迁移原位重命名为 `platform_channels`、`personal_channels`、`personal_channel_model_routes`。迁移保留原记录及 ID，不复制后删表；如新旧表同时存在则中止迁移，避免覆盖或丢失数据。
- 历史 `personal:` 渠道 ID、`personal_provider` 日志来源值和既有 HTTP 路径在兼容期保持稳定；新代码和新文档使用“个人渠道”概念。兼容只保留历史数据/API 值，不继续保留旧的 Go 模型命名。

```text
消费者 Token
  ├── 有序分组选择：[G1, G2, G3]
  └── 可用范围 = Token 配置 ∩ 消费者有效权益
                         |
                         v
                 分组 G 的候选池
                 ├── 平台渠道
                 ├── 已获所有者授权的个人渠道（共享供给）
                 └── 已审核报价/其他适配供给
                         |
             按组内路由策略选择一个成功上游
                         |
       消费者按 G 定价；平台和实际供给者按规则分成
```

平台默认分组是一个平台管理的默认服务分组；个人连接与该组的关系带有所有者范围，不能把不同用户的连接混在一个公开候选池中。收费分组的个人渠道关系则是所有者明确授权的共享供给关系。

平台管理员负责创建分组并配置分组服务。用户侧只消费平台开放的分组权益并管理自己的 Token 顺序；个人渠道所有者可以从平台开放的收费分组中选择是否授权共享。组内渠道候选是否通过审核、何时启用以及组内路由和价格由平台管理员管理。平台可定义候选准入条件并自动检查，不能把分组配置权交给普通消费者或个人渠道所有者。

初次选路时，如果该组没有符合模型、端点、Token 范围和候选授权的渠道，按顺序继续检查下一组；这属于查找可用服务，不依赖请求内重试开关。只有某上游已被调用并返回故障后，才由 Token 自动切换设置和 `RetryTimes` 分别决定是否继续尝试候选。

## 4. Token 有序分组

### 4.1 建议的行为

- 每个 Token 有自己的分组顺序，同一用户可让不同 Token 使用不同顺序。
- 有效候选组是“Token 顺序中出现的组”与“用户当前有效权益组”的交集，再受 Token 模型范围及其他访问规则收窄。初次选路会跳过当前请求无候选的组并继续查找；这不代表故障重试。
- 更新 Token 顺序时只接受当前用户可访问的分组 ID；重复、未知或已撤销授权的项目应拒绝或清理，不能被当作权限授予。
- 阶段一创建 Token 时，用户界面将当时有效权益组按来源优先级、名称和 ID 稳定排序，并随 Token 一起保存；用户可在保存前调整。之后新获得的分组会在 Token 页面现有顺序之后显示，直到用户保存时才写入。失去权益的组不会参与请求或显示；用户下一次保存 Token 时，存储顺序会替换为当时的完整有效权益组集合，因此撤销后再恢复权益不会保留已被替换的旧位置。
- 每次请求开始时读取并固定一份顺序快照；请求中修改 Token 不影响已开始请求。
- Token 列表为空的兼容行为建议为：临时按当前有效权益的稳定排序生成顺序，并在用户下次保存 Token 时持久化。上线前需确定这个兼容期是否允许。

### 4.2 数据表达建议

首选独立关系表，例如 `api_token_group_routes`：

| 字段 | 用途 |
| --- | --- |
| `token_id` | API Token |
| `group_id` | 分组 |
| `order_index` | 用户设置的顺序，数字越小越先尝试 |
| `created_at` / `updated_at` | 审计和配置变更 |

唯一约束建议为 `(token_id, group_id)`，并确保同一 Token 的 `order_index` 不冲突。该表表达偏好顺序，不单独构成授权。相比在 Token 上放 JSON 列，关系表便于排序、唯一约束、部分更新和查询有效权益交集。

### 4.3 需要保留的兼容决策

当前 `api_tokens.route_policy` 表达 `personal_first`、`personal_only`、`community_first`、`community_only`。新分组顺序不能静默抹掉这些既有来源限制。建议迁移期间保留并读取旧值作为来源过滤约束；新 Token 使用分组路由配置。逐步确认旧值如何映射后，才可停用字段。不得把 `personal_only` 自动扩张成“允许任意收费组中的个人供给”，也不得把 `community_only` 解释为所有平台分组。

## 5. 默认组与收费组个人渠道授权

### 5.1 用户添加渠道

1. 用户登录并提交协议、Base URL、模型声明和凭据。
2. 分组字段默认选择平台默认分组；界面说明该组只供本人使用。
3. Router 执行既有的凭据加密、协议校验和连接验证。
4. 默认组模型以私有视图展示为该用户个人连接模型与端点的交集，不写入共享 `group_models`。
5. 个人渠道的自用调用继续遵守 Token 次数、速率和安全规则；其上游账单由该连接所有者与上游供应商结算。

### 5.2 加入收费分组

所有者从自己可管理的连接中选择平台开放申请的收费分组，明确确认共享授权、允许暴露的模型/端点、数据处理说明和平台分成规则版本。授权通过后，只有与收费分组逻辑模型/端点相交、且连接确实支持的能力可进入候选池。平台管理员负责审核并决定候选是否进入组路由，且可暂停或移除候选；所有者不能自行修改收费组的模型范围、售价、路由策略、审核结果或分成比例。

建议新增所有者授权关系（概念名 `group_personal_channel_bindings`），字段至少覆盖：分组 ID、个人连接 ID、所有者用户 ID、启停状态、候选优先级、授权/撤销时间、授权条款版本、平台分成规则版本、创建/更新操作者。候选优先级由平台管理员维护。唯一约束应防止同一连接重复加入同一组。该关系不复制凭据，也不让该连接进入别的分组。

当前 `group_channels` 只解析普通平台 `Channel`，`group_model_channels` 也以现有平台渠道表作为来源。实现时应通过统一候选接口把个人连接适配为路由候选，并在候选过滤中校验所有者授权；不应仅把 `personal:<id>` 写入旧表后假定现有查询、静态展开、管理端和采购归因都能正确处理。

### 5.3 撤销、禁用和故障

- 所有者撤销收费组授权后，立即禁止新请求选中该候选；进行中的请求是否允许完成，建议按请求开始时的授权快照完成，并记录撤销时间。
- 所有者禁用或删除个人连接后，所有收费组绑定同时变为不可用；删除前应说明对正在服务的消费者的影响。
- 平台管理员可单独暂停该候选，不改变所有者凭据或默认组自用能力。
- 连接验证失败、健康熔断和人工暂停是不同状态；恢复健康不得自动恢复已撤销的所有者授权。
- 共享候选需有并发/速率保护、可观测性和数据去向说明。消费者只看服务提供者可公开的标识、能力、区域/数据说明和结果，不看 Base URL、密钥或私人连接名称。

## 6. 请求路由算法

1. 鉴权 Token，固定 Token 模型范围、组顺序、自动切换设置和额度快照。
2. 解析本次逻辑模型与端点；筛出 Token 顺序中用户仍有有效权益且模型范围允许的分组。
3. 按顺序读取一个分组的候选：平台渠道、已授权给该组的个人渠道、以及该组允许参与的其他供给候选。
4. 对每个候选统一校验渠道状态、模型映射、端点能力、来源/`provider_scope`、个人所有者共享授权、容量和健康状态。
5. 按分组优先级/权重策略选候选。组内候选耗尽或没有候选时，检查是否允许继续；用户本地额度、Token 权限和客户端错误直接终止。
6. 收到可切换的上游 HTTP 渠道级错误时，自动切换开启则尝试本组下一候选；明确传输错误仅在 `RetryTimes` 允许时尝试其他候选。
7. 已发生上游调用且本组候选耗尽后，仅当对应错误类别的切换规则允许时，进入 Token 顺序里的下一授权组；再次检查其权益、模型、端点、消费者额度和价格规则。若初次选路阶段本组根本没有合规候选，则不受故障切换开关限制，直接查找下一组。
8. 结算只以最终成功响应对应的分组和渠道为准。失败候选保留在尝试记录中，但不取得成功调用分成。
9. 显式指定单个渠道、显式报价固定路由和已绑定状态会话沿用各自明确语义，不因分组顺序默认扩大其候选集。

## 7. 消费者计价与平台/所有者分成

### 7.1 价格和收入分开

- **消费者服务价格**：由最终命中的分组和模型规则确定。同一组同一逻辑模型的消费者价格不因命中平台或个人渠道而变化。
- **供给分成**：成功调用后，将可归属给该次调用的消费者已售收入按适用的版本化规则在平台与实际个人渠道所有者之间分配。这是供给应付，不是用户额外扣款，也不是平台的上游采购成本。
- **个人上游套餐费用**：由个人渠道所有者在平台外购买并承担。费用可能是固定月费或预付套餐，不一定能按单次调用精确归属。
- **个人渠道供给收入**：所有者共享未用完的模型能力后，从实际成功调用对应的分组收入中取得约定份额。它是额外供给收入，可帮助所有者摊薄外部套餐成本，不是 Router 对外部账单的报销。

#### 收入归属方案（待评审，不代表当前实现）

建议把消费者实际支付的净收入作为收入池，再把成功请求按其实际消费的权益来源归属到相应收入池；不能把 `BillingSettlement.ChargeAmount` 或 `YYC` 消耗直接称为现金收入。`YYC` 可用于计算请求在某个收入池内的分摊权重，但所有者应收仍须受该池实际净收入约束。

| 消费者本次权益来源 | 建议的收入池和分摊权重 | 处理规则 |
| --- | --- | --- |
| 直接余额 / 充值余额 | 以余额批次关联订单的实收净额为收入池；以请求实际从该批次扣除的 YYC 占该批次已售 YYC 的比例分配 | 一个请求跨多个批次时，分别记到各批次收入池。赠送/后台赠余额不产生消费者购买收入；若平台希望活动也能获得供给服务，须由明确的活动预算出资 |
| YYC 额度订阅 | 以订阅购买/续费周期的实收净额为该周期收入池；周期内从订阅额度成功结算的 YYC 消耗可作为请求间分摊权重 | 当前订阅规则是日额度、应急额度和有效期，不是“订单售出固定总 YYC”；因此不应直接用 `订单实收 × 单次 YYC / 名义套餐总 YYC`。建议在周期关闭后按周期内符合条件的已结算 YYC 消耗分摊，超赠额度须单独标识，退款从池中冲减 |
| 按次订阅 | 以订阅购买/续费周期实收净额为该周期收入池；以成功结算的付费请求次数分摊 | 只对实际由该订阅扣除的一次计数生成权重；免费/赠送次数由促销预算另行承担或不分成。升级、续费和周期重叠要按订单/订阅周期分别建池 |
| 促销、赠送或零价权益 | 默认没有消费者收入池 | 只有活动预算明确承担供给分成时才生成分成，不能从平台留存或个人所有者收入中隐式补足 |

一次请求可能由套餐和余额兜底共同承担；应按真实结算来源分拆到各收入池，再依据最终命中的个人渠道分成规则计算所有者应收。当前消费日志只保留一个 `billing_source` 快照；余额批次扣减虽逐批写交易，但请求级扣减结果没有记录每个批次各自扣减量，套餐订阅也没有固化购买收入及分成周期快照。因此现有日志不足以直接完成上述分摊，不能仅根据请求总 `ChargeAmount` 或首个余额批次推断收入来源。实现前需设计逐来源结算明细和不可变收入池快照。

余额批次应以对应购买订单中的实际实收净额和到账 YYC 为基础，不能用当前兑换率反算。套餐收入池则必须对应实际购买/续费/升级订单，保存订单实收、币种、折扣/退款、权益类型、赠送部分和服务周期。周期型 YYC 订阅若采用“周期内实际消耗权重”，供给收入需要先暂记，周期结束且退款/拒付窗口规则明确后再最终结算；若要请求完成即确认应付，则需评审另一套预估和追索规则。

建议以变量表达：

```text
本次可分配收入 = 按实际扣费权益来源分摊到该成功请求的已售净收入
个人渠道所有者应收 = 本次可分配收入 × owner_share_bps / 10,000
平台留存收入 = 本次可分配收入 - 个人渠道所有者应收 - 明确列账的税费/退款/风险准备
```

示例（仅适用于有固定付费 YYC 数量的余额批次）：消费者以 100 元购买 10,000 YYC，其中不含赠送额度；若一个成功请求从该批次实际扣除 50 YYC，则该请求对应 0.50 元购买收入。周期型订阅不能直接套用这个例子，因为它的订单可能售出的是一个期限内按日重置的使用权，而非固定 10,000 YYC。个人所有者承担自己平台外的月费/套餐成本，所得分成是分享剩余能力获得的额外收入，可以帮助摊薄成本；Router 不采集所有者实际套餐账单，也不保证分成覆盖成本。

建议采用以下结算时序：请求成功后只生成“待周期确认”的供给分成记录；消费者套餐/订阅权益周期结束后，按该周期内实际成功消耗的权益权重分摊该周期实收净收入，并确认所有者应收。周期结束不等于立即付款：仍在退款、拒付或争议窗口内的金额继续冻结，之后进入固定结算批次。余额批次不属于套餐周期，按平台统一的自然月结算周期归集；余额批次收入池耗尽后不得继续产生应付。每笔记录保留权益周期、收入池、平台分成规则版本和汇率快照，不能追溯修改。

这里的“周期”建议指消费者购买的套餐/订阅权益周期，而不是渠道所有者外部模型套餐的周期；平台外套餐费用由所有者自行承担。按次订阅的一次购买周期内，已成功消费次数作为分摊权重；YYC 订阅则使用周期内实际结算 YYC 消耗作为权重。订阅续费应形成新的收入池；升级、退款或周期被替换时，按订单和实际生效区间拆分收入池。余额批次按其购买订单实收净额与批次到账 YYC 的比例归集请求分摊额。任何一个收入池的累计分摊不得超过其可分配净收入。

**分成比例建议**：分成比例由平台统一设置，收费分组和个人渠道所有者均不能单独调整或议价。同一平台规则下的个人渠道使用相同比例。个人渠道提交加入申请前，必须看到平台当前比例、计算基数、冻结期、结算币种和撤销规则并明确接受；平台调整比例后，新比例只适用于调整生效后开始的消费者权益周期，以及生效后发起的余额扣费请求。已开始的订阅周期和历史请求按已冻结的规则版本处理。具体比例数值仍待评审。

**结算币种建议**：所有者应收账本和平台结算批次首期统一使用 CNY，与 Router 当前财务基础币种一致；不使用 YYC 作为可提现应付。消费者购买订单若以其他币种付款，在订单履约时按实际支付/入账汇率固定其 CNY 净收入快照，收入分摊沿用该快照，不在供给结算时按当前汇率重算。账本同时保留原订单币种、原始净额、汇率和 CNY 金额以便审计。若未来开通外币付款，再新增明确的币种选择和换汇流程，不能让每个渠道所有者自行选择币种造成多币种欠款。

仍需评审：`owner_share_bps` 的具体平台设定值；可分配净收入扣除支付手续费、依法应计税费和风险准备的具体顺序；退款、拒付、舍入和负向应付抵扣规则；请求成功的计量真值及按次请求定义；结算批次频率、最低付款额、冻结窗口和实际付款方式。Router 的 YYC 消耗只表达权益结算，不等于现金收入；必须从对应订单或余额批次的实收建立收入池。

消费者价格的目标配置在分组/模型层。当前 `group_channels.billing_ratio` 和 `group_model_channels.billing_ratio` 可能让同组同模型因命中不同渠道而产生不同售价；这与“切换渠道不改变消费者价格”冲突。迁移时应折算或合并进分组/模型售价规则，目标候选路由不得按最终渠道套用消费者售价倍率。

### 7.2 结算记录

现有 `billing_settlements` 保存消费者侧请求价格和 usage，`procurement_attributions` 保存平台渠道采购成本；开放供给已有 `PublisherOfferSettlement` / `PublisherSettlementDelivery` 记录报价收入分配，并通过请求日志 ID 实现幂等和跨日志库交付。个人渠道分成应复用这套“请求级不可变快照 + 幂等交付 + 单独应付账本”原则，不能写进 `procurement_attributions` 冒充采购成本。

可选实现方向是在结算域扩展通用供给结算记录，并增加请求级权益来源明细；记录应明确 `provider_type`（publisher 或 personal channel）、`provider_user_id`、`provider_resource_id`、`group_id`、`consumer_user_id`、`request_log_id`、最终渠道/模型、每一项权益来源、关联订单/订阅周期/余额批次、该收入池净额及分摊权重、该请求分摊的净收入、平台/所有者分成额、规则及汇率版本、币种快照和状态。相同请求 ID 只允许结算一次；退款或争议以反向分录关联原记录，不覆盖原快照。已发放的应付发生退款或拒付时，生成负向调整并从未来应付抵扣；不得删除或改写原分录。是否扩展现有发布者账本或新增个人渠道应付账本，是实现前需评审的数据选择。

个人渠道供给收入只在有成功 usage/最终消费者结算事实且存在已售收入来源时生成；部分计量、免费额度、预扣后失败、退款或无法确认 usage 的请求，按既有结算真值分类制定规则，不能简单以“HTTP 200”作为唯一应付条件。个人所有者的月费/套餐账单是其平台外成本，不要求与某一条 Router 请求一一对应，也不直接进入 Router 采购成本账本。

## 8. API 与页面行为建议

- Token 创建/编辑页展示已授权分组的排序控件；不可授权用户没有权益的组。保存后返回规范化顺序及被移除的过期组原因。
- 新增权益组自动出现在 Token 顺序末尾并提示用户；撤销权益后该组从实际候选中剔除。用户可拖动顺序，不需要理解“主组/备用组”以外的底层权益来源优先级。
- 添加个人渠道页默认选中平台默认分组，清楚标注“仅你可用”。
- “加入收费分组”是独立的显式操作，列出可加入分组、开放模型/端点、收入分成规则、数据处理说明、容量要求和撤销效果。授权后显示审核/启用状态和实际调用收入。
- 收费分组管理页仅供平台管理员配置分组模型/端点、消费者价格、路由策略、渠道候选和平台统一分成规则，并在同一组内治理平台渠道及已授权的个人供给候选。候选来源/所有者作为治理字段，不形成第二套路由策略；个人渠道所有者只能管理自己的连接和授权，不能编辑分组配置。
- 消费者调用记录显示实际分组、模型、公开的供给者身份、是否发生组间切换及实际扣费。个人所有者看自己的调用量、分成应收和结算状态；看不到消费者不必要的个人信息。

## 9. 迁移与分阶段启用

按“每阶段完成、生产升级、观察通过后再进入下一阶段”推进。生产升级指发布该阶段代码/数据库变更；每个有用户可见影响的功能仍需由功能开关控制并逐步放量。任何阶段都不自动启用尚未评审的收费、个人供给或付款能力。

1. **阶段一：Token 分组顺序基础。**已新增 Token 有序分组配置的持久化/API 和用户管理入口；只接受用户当前有效权益里的完整分组集合，创建和更新 Token 与顺序在同一事务中提交。此阶段不新增个人渠道共享授权、不改组配置、不让新顺序参与真实选路；保留旧 `route_policy` 与旧路由行为，不删除或重写历史账单。生产已升级；该顺序目前仍未接入真实 relay 选路。
2. **阶段二：移除影子逻辑并建立 Tester E2E 验收。**影子逻辑清理已获确认，本次从 Router 移除影子队列、查询、配置、上下文标记和诊断日志；停止通过生产影子流量验证。同步在 Tester 建立分组顺序和跨组路由的 E2E 用例，先评审场景和错误边界，再实现测试。测试必须运行在隔离的 Router/数据库及受控上游环境，不能对生产流量、账务或渠道做验证。
3. **阶段三：平台渠道分组路由。**在 Tester 验收场景明确后实现真实分组路由；只覆盖评审确认的无状态请求，严格沿用 Token 权限与 `RetryTimes` 边界，不改变分组价格。先由 Tester 在隔离环境验证通过，再决定后续部署和放量方式。
4. **阶段四：个人渠道授权与共享试运行。**增加所有者授权、平台管理员审核、组内候选管理、容量保护和消费者数据告知；先使用测试供给或隔离限量服务。只有审核责任、准入标准、请求数据范围、并发/速率上限、撤销生效边界明确后，才开放真实消费者流量。个人渠道默认仍只供本人使用。
5. **阶段五：供给收入核算。**新增请求级权益来源明细和收入池快照；先按已确认的 CNY 规则生成影子分成并与账务对账，不生成可提现应付。要通过套餐/余额混合扣费、跨批次余额、周期结束、退款/拒付、升级续费、舍入和幂等对账。
6. **阶段六：应付确认与付款。**平台统一分成比例及版本生效规则、净收入扣减顺序、风险冻结窗口、结算批次频率、最低付款额、收款资料/审核和实际付款方式定案后，才把影子金额转为真实应付并执行首批付款。先小额人工复核，完成对账再扩展。
7. **阶段七：兼容迁移和扩展。**确认旧 `route_policy` 映射、用户迁移体验和回退方案后，再逐步替换旧来源策略；状态会话、异步任务、更多供给类型和规模扩张另行评审，不随前序阶段默认纳入。

任一阶段发生越权、跨组错误扣费、所有者凭据泄露、重复应付或 Token 顺序丢失，应能通过功能开关退回旧路由；新旧日志保留足够字段定位差异。

### 9.1 Tester 分组路由 E2E 验收方案（待评审）

**目的：**用可重复、可控的请求验证 Token 分组顺序、用户有效权益、组内渠道选择、组间回退和账务归属。验证由 Tester 在隔离环境完成，不以生产流量样本作为验收条件。

**当前实现边界：**阶段一只持久化 Token 的 `group_route_order`；当前 relay 尚未读取该顺序做分组路由。Tester 用例将定义未来真实分组路由的验收标准。用例文档评审通过后可先实现测试框架；在 Router 路由能力交付前，相关行为用例应标记为待目标实现，不得把未通过或跳过误报为功能通过。

**隔离要求：**使用专用测试 Router 实例、独立且可重置的测试数据库、专用测试钱包/Token/管理员凭证，以及 Router 可访问的受控上游 stub。测试创建的分组、模型、渠道、权益、令牌和请求账务都限制在该环境。任何会启用候选渠道、发送中继请求或扣减额度的用例，不得指向生产或共享的真实用户账务环境。Tester 增加显式启用保护；缺少保护配置、目标 URL 不符合测试环境约束或上游 stub 不可达时，测试必须停止/跳过并说明原因。

**拟覆盖的行为：**Token 顺序仅在用户当前有效权益中生效；首组无匹配模型/端点渠道时继续下一组；组内可切换候选，允许的渠道级不可用错误耗尽本组后再进入下一组；明确网络传输错误的重试次数严格服从 `RetryTimes`；权限、用户额度、非法请求和客户端取消不应被当作可重试网络故障；无候选时返回受控错误且账务不重复扣减；显式渠道和有状态 Responses 继续遵循各自已确认的边界。完整场景草案见 Tester 仓库的 Router 用例目录。

**实施顺序：**先评审 Tester 用例和尚未定案的错误分类、空 Token 顺序兼容、实际扣费归属、状态会话范围；通过后实现 Tester 用例和隔离配置；再用受控目标部署验证用例执行及资源清理；之后另行实现和评审真实分组路由。

**影子逻辑下线（清理范围已确认）：**本次移除影子任务队列、后台工作协程、影子候选及端点查询、影子专用只读权益查询、专用仓储接口、相关上下文标记、四个 `relay.group_route_shadow_*` 配置项、allowlist 归一化工具、诊断日志及专用测试。现有真实选路、渠道故障转移和 Token 分组顺序持久化不变，不做数据库迁移或数据删除。新版本部署后不再执行影子任务；部署配置也应删除上述四个配置项。现有 YAML 加载器会忽略遗留未知字段，它们不再产生任何运行效果，不另设兼容代码。

## 10. 评审决策清单

以下项目按阻塞阶段区分；未定事项不得被实现成默认产品行为。

**阶段一采用的行为：**新 Token 初始化为创建时的有效权益组稳定顺序；新权益组在现有顺序后显示并在用户保存后写入；权益撤销后不展示该组，下一次保存会以当前完整权益组集合替换旧顺序。旧客户端不提交 `group_route_order` 时保留已有顺序；阶段一不改变旧 Token 路由。生产升级后需验证迁移、读写和越权拦截，再观察后进入阶段二。

**阶段二已确认与待评审边界：**取消生产影子路由并清理 Router 实现已确认，本次执行。Tester 独立环境的 E2E 验收方案仍待评审，评审内容包括本文件 §9.1 与 Tester `docs/test-cases/router.md` 的候选场景，重点确认错误分类、空顺序兼容、账务归属、状态请求范围和测试环境隔离。

**进入阶段三前需要确认：**平台渠道组间路由所需的权益判定来源、空顺序兼容行为、旧 `route_policy` 的过渡约束、错误分类和回退观测指标。状态会话与跨模型降级不在范围内。

**进入阶段四前需要定案：**收费组个人供给审核责任及驳回/申诉流程；请求数据范围、消费者告知和地区/留存要求；并发/速率/SLA 和连续故障暂停规则；所有者撤销、平台暂停、删除连接对进行中流式请求的生效边界。

**进入阶段五前需要定案：**平台统一分成比例的具体数值和版本生效时点；消费者实收净收入的手续费、税费、退款、拒付及风险准备扣减顺序；CNY 订单换汇快照来源；YYC 订阅、按次订阅、余额批次、赠送权益和升级续费的收入池规则；小数舍入、负向应付抵扣；是否复用 publisher payable 账本。所有者平台外套餐费用仍由所有者承担，供给分成不是上游费用报销。

**进入阶段六前需要定案：**冻结期、结算批次频率、最低付款额、收款资料/KYC 与税务要求、付款渠道和付款失败/争议处理。此前只允许影子核算，不得生成可提现应付或真实付款。

## 11. 当前代码对照

- Token 保留原有 `route_policy`，并新增独立的 `api_token_group_routes` 表保存每个 Token 的分组顺序；创建/更新接口校验顺序必须完整匹配用户当前有效权益组，组顺序与 Token 基础信息在同一事务提交。用户 Token 页面可查看和调整顺序。当前 relay 仍不读取该顺序，旧 `route_policy` 和请求路由行为保持不变。
- `PersonalChannel` 通过 `personal_channels` 保存个人模型和加密凭据，路由适配为 `ChannelCandidate`；尚无分组授权关系。
- `group_channels` 绑定 `platform_channels`；当前不能直接容纳个人渠道。
- `BillingSettlement`、`ProcurementAttribution` 已分离消费者价格和采购成本；个人渠道供给应付还没有对应账务记录。
- 当前套餐/订阅运行数据不能代表不可变的购买实收与分成周期快照。余额消费日志只记录一个来源快照，无法表达一次请求跨多个余额批次的实际扣减构成。正式分成前，需增加请求级多来源结算明细，并在订单履约时保存收入池快照；订阅分摊要按最终选定的周期规则实现，不能假设现有订阅售出固定总 YYC。
- `PublisherOfferSettlement` 已有发布者报价分成快照和交付模式，但其报价/发布者身份模型与个人渠道所有者不同，需要评估复用或统一，而不能混用 ID。
